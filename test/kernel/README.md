# Integration VM kernel configuration

`aya_aarch64.config` and `aya_x86_64.config` are KCONFIG_ALLCONFIG request
fragments for the integration VM kernels declared in `BUILD.bazel`.
`linux.bzl` resolves each fragment from `allnoconfig` using the
integrity-pinned Linux source and the configured LLVM platform.

The fragments contain requested values, not complete Linux `.config` files.
Linux Kconfig adds defaults and values derived through dependencies, `select`,
and `imply`. Keep an assignment in a fragment when an integration VM requires
the value or when the assignment intentionally pins a Kconfig default. Do not
copy generated values from a resolved `.config` into a fragment.

Linux's own `conf` resolves configurations during build execution, using the
selected compiler and BTF encoder for capability probes. Kbuild planning reads
the native configuration and Make values. Before compiling the kernel, the
build checks the required integration options declared in `kernel.bzl`.

Both fragments build `sch_ingress.ko` as a loadable module. The VM initramfs
includes that module and an alias file generated by `test-distro:depmod`, so
the `modprobe` integration test exercises the kernel's usermode helper.

CI tests Linux 5.10, 5.15, 6.1, 6.6, 6.12, and 6.18 on both guest
architectures. Each VM runs the default and optimized Rust test binaries,
built with stable Rust for userspace and nightly for eBPF.
Kernel patch versions and archive checksums are pinned in `MODULE.bazel`.
Each kernel line has one configured build under
`//test/kernel:kernel_<line>`; its target platform selects the architecture.
The boot image, resolved configuration, symbol table, and ingress module are
selected from that same build. The package and VM target names stay the same
across patch updates.

`kernel.BUILD.bazel` exposes the files in each Linux source archive. The VM
initramfs uses Linux 6.18's `gen_init_cpio` for every guest version, with fixed
timestamps, root ownership, and explicit file modes. The archive is built on
Linux, including when QEMU runs on macOS.
The kernel builds and VM tests are manual targets, selected explicitly by CI.

## Kernel build tools

Use Bazelisk to select the Bazel fork pinned in `.bazelversion`. The fork
supports per-action compiler input discovery, so dependency scans can declare
the individual files each compilation reads. Upstream work is tracked in the
[input discovery proposal](https://github.com/bazelbuild/proposals/pull/422)
and [expanded-action query change](https://github.com/bazelbuild/bazel/pull/31850).
The fork can be removed when an upstream release provides those interfaces.

Source packaging uses `/usr/bin/find` on Linux and macOS to locate directories
containing native `Build` files. Generated `BUILD.bazel` metadata keeps them in
Bazel's source inventory on case-insensitive filesystems, preserving Linux's
filenames and contents.

Bazel builds Linux's source-selected Kconfig resolver as a declared tool. A
shared GNU Make exporter parses each source tree into symbolic syntax during
repository loading, without resolving a configuration or probing a compiler.
Full kernel builds consume that syntax alongside the native configuration;
configuration-only builds do not load it. The kernel archives and build tools
are pinned in `MODULE.bazel`; `kbuild_exporter.json` pins the exporter archives
for Linux x86_64 and macOS AArch64 hosts.

Kernel C compilation uses separate Clang frontend and backend actions. The
backend can share cached objects when configurations produce identical
bitcode and backend inputs, using the output path mapping settings in
`.bazelrc`.

## Remote builds

The commands below use Aya's remote BuildBuddy service, which requires an API
key. From the repository root, read the intentionally public CI credential and
set the arguments once in your current shell:

```console
$ aya_buildbuddy_key=$(awk '$1 == "BUILDBUDDY_API_KEY:" { print $2; exit }' .github/workflows/ci.yml)
$ aya_remote=(--config=remote
    --remote_header="x-buildbuddy-api-key=$aya_buildbuddy_key"
    --remote_downloader_header="x-buildbuddy-api-key=$aya_buildbuddy_key")
```

## Reproduce the resolved configurations

From the repository root, resolve both fragments with:

```console
$ for arch in aarch64 x86_64; do
    bazel --host_jvm_args=-Xmx8g build "${aya_remote[@]}" \
      --lockfile_mode=error \
      --platforms=@rules_rs//rs/platforms:${arch}-unknown-linux-musl \
      //test/kernel:kernel_6_18_configuration
  done
```

Use `bazel --host_jvm_args=-Xmx8g cquery "${aya_remote[@]}" --output=files` with
the same platform and label to print the configuration output directory;
`.config` is inside it. Add
`--remote_download_outputs=toplevel` to the build command to read it locally.

After changing either fragment, rebuild both resolved configurations and run:

```console
$ bazel --host_jvm_args=-Xmx8g test "${aya_remote[@]}" --lockfile_mode=error \
    --@rules_rust//rust/toolchain/channel=stable \
    //test/integration-test:vm_aarch64_6_18 \
    //test/integration-test:vm_x86_64_6_18
```

Replace `6_18` with another kernel line, such as `5_10`, to run its tests.
The VM targets are manual and CI invokes each kernel line explicitly.

## Run a VM on macOS

The local macOS VM target uses Homebrew QEMU. The kernel and test binaries
can still build remotely. Install QEMU and select its toolchain explicitly:

```console
$ brew install qemu
$ bazel --host_jvm_args=-Xmx8g test "${aya_remote[@]}" --lockfile_mode=error \
    --@rules_rust//rust/toolchain/channel=stable \
    --platforms=@platforms//host:host \
    --extra_toolchains=@homebrew_qemu//:x86_64 \
    //test/integration-test:vm_x86_64_5_10_macos
```

CI runs this x86_64 guest on macOS; it uses software emulation on ARM hosts.
